# Candidates

1. Run `python3 -I .claude/skills/routine/check.py --only candidates`. If dispatcherctl says the session expired, ask the owner to run `! ~/go/bin/dispatcherctl login`.
2. Answer waiting proposals first, following the **Proposals** bullet in `.claude/skills/routine/SKILL.md`.
3. If more than 10 earning templates are under 70% health (`--only health`), say to fix before publishing. Every new template adds to the health and upgrade load for good.
4. Nothing reaches the shortlist unless someone puts it there, and the owner rarely does, so filling it is this skill's job. Start from the most deployed apps we don't publish (the report's market list), skipping groups already marked skip. For each, check that it runs as a Railway service and who holds the market: vendor-owned deploys and features Railway IPs can't do have sunk picks before. Search `templateSearch` for every variant of the name before calling it open.
5. Read each surviving keyword the way search will rank it with `python3 -I .claude/skills/candidates/opening.py "KEYWORD" ...`. It lists the top 10 with tier, health and active projects, says whether the keyword's exact slug is free, and estimates where a new exact-name template would land: unscored at first, then at 100 once someone else's deploy runs it, then with 20 active. With three or more exact-name listings at 100 and many active, we start at #4 or lower and stay there until our active count passes theirs. If they're unscored or under 70, a healthy exact-name template takes #1, and when tier 0 is empty even an unscored one does, within minutes of publishing ("Linux", `ssh`, `mint` on 8–9 Nov). Plan on the unscored position until outsiders deploy it: our own held deploys never give a score (tested 8–9 Nov).
6. Mark every pick that passes both checks with `~/go/bin/dispatcherctl candidate KEY shortlist "NOTE"`, KEY as the Candidates page groups it. The note is one line the owner reads on the page: the demand, the position we'd start at and why, and the main risk, e.g. "1.2k deploys/90d; tier 0 has one 100 with 2 active, so #2 at 100 then #1; needs a GPU-free model". Keep 3–5 on the shortlist. Mark a pick that fails with `skip` and the reason, so the next check doesn't read it again. Take an app off the shortlist (`""`) when a rival fills the opening.
7. Judge an original on its own terms, never on kickback math alone. Check the "ours, but others take most" list too, since fixing a listing is cheaper than building.
8. When building, name and slug it for search. Only the name, slug and description are searched, not the readme or tags. Search matches the start of words: no stemming, no typo tolerance. So the name is the app's exact name with no tagline: a " | tagline" drops it from the exact-name tier to "starts with" (Heimdall's "SearXNG | …" at 100 health with 121 active ranks under every bare "SearXNG"). Add a tagline only when it wins a bigger generic word than the name loses. Secondary words go in the description. The slug is first-come and can never change: claim the bare app name, never `-production` or `-1`. If it's taken, take the slug for the highest-demand phrase instead (`ubuntu-terminal`, `linux-desktop-kde`). If a template went out under a worse slug, republish it under the right one while it has 0 deploys and delete the old one, as Linux Mint moved from `linux-mint` to `mint` on 9 Nov.
9. Recommend one or two from the shortlist, and wait for the owner's OK before building. The shortlist is advice: the owner skips or clears marks on the page.
