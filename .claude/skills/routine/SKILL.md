# Routine check

The routine is the checklist at https://claude.ai/artifact/2vHDWt6gxBdmWuGYEyEqMo (source: `page.html` here). Health first, because health holds search position and position drives deploys. Then publish. Upgrades, search, the verdict and payouts are weekly.

This is the overview, and its bullets below hold the rules. To work one area, the owner uses `/health`, `/upgrades`, `/search`, `/candidates`, `/verdict`, `/payouts` or `/catalog`, which follow the same rules and don't reset what this check compares against.

## Steps

1. Run `python3 -I .claude/skills/routine/check.py`. It reads live figures with `~/go/bin/dispatcherctl` (logged in to dispatcher.zaur.app), prints a report, and saves them to `last.json` so the next check can say what moved. If dispatcherctl says the session expired, ask the owner to run `! ~/go/bin/dispatcherctl login`.
2. Run `python3 -I .claude/skills/routine/check.py --only payouts` and look only for a failed or missing transfer.
3. Answer in this order, short, with one recommendation per section:
   - **Proposals:** the owner adds links on the Candidates page. Evaluate each waiting one the way a pasted link is evaluated here (what it is, whether it runs as a Railway service, the market for it), then answer it with `dispatcherctl proposal URL STATUS "REPLY"`: `skipped` with the reason, or `building` when you start it and `published` with the template code once it's live. Keep a reply to one or two sentences; the owner reads it in Dispatcher. Ask before building if more than one is worth it.
   - **Health:** name the earning template to fix first, skipping any marked `fix pushed`: health scores the deploys already running, so it lags a fix until deployers take the update or new deploys land. Whenever a health fix is pushed, record it with `dispatcherctl fixed ID YYYY-MM-DD`; if a fixed template is still low a few weeks on with new deploys since the fix, the fix didn't hold. If it has pending upgrades, they go into the same push as the fix, majors included: every push notifies the deployers, so one change means one notification. Only a major that has to migrate data, such as a database, stays out and gets its own tested change. More than 10 earning templates under 70% means fix before publishing.
   - **Since last check:** recovered or new low-health templates, new templates published, any templates still missing a kind or origin. Offer to set them. Origin means original (no other creator had the same app on Railway before ours was published) or competitive; set it with `dispatcherctl origin ID original|competitive`, and leave a template unmarked when you're unsure.
   - **Upgrades:** weekly, counted from the last upgrade push, never from the last check: a check that only read the queue upgraded nothing. The report prints the last recorded upgrade day and whether the section is due. Record every push with `dispatcherctl upgraded ID YYYY-MM-DD`, one call per template in it, on the day you push. The daily 06:08 check also sets the date when a pinned tag it reads changes, but only the morning after, and only for pins it can read. Urgent first: read the release notes between our tag and the latest for every template with running instances, and flag a security fix (CVE, advisory, auth or permission bypass) or a fix for something our version breaks on. Urgent ones go first, most running instances first, since exposure is per deploy, not per dollar, earning or not. Record each with `dispatcherctl urgent ID "REASON"` (one line, e.g. "CVE-2026-1234: auth bypass in share links"), so the Upgrades page leads with it; the daily check clears the flag once the template is current. When nothing is urgent, work the queue for money: behind first, then by 30-day earnings, running instances breaking ties. Batch per template, and hold a release that is days old with an open regression report in favour of the last patch before it.
   - **Candidates:** if the report says the shortlist has fewer than 3, fill it as `/candidates` does (steps 4–6 there), and say what you added. Only the owner's OK starts a build.
   - **Search:** dropped or missing own keywords, read with the ranking rule in `docs/research/railway-search-ranking.md`: text tier first (name equal to the query, or slug equal with the query's words in the name, then name starting with it, then name containing the words, then slug or description only), then health band (exactly 100, then 70–99 as one flat band, then unscored, then under 70), then running deploys. So a drop within the same tier is health leaving 100, falling under 70, or a rival with more running deploys; 96 and 70 rank the same. Under 70 costs more than the band: it can sink a template under rivals a tier or two lower (exact-name Claude Code at 50 was #22 for "claude code"). A template with no active projects has no score and sorts under every 70+ rival in its tier, and our own deploys never give it one (tested 8–9 Nov): only someone else's active project does. The readme, tags and creator don't move rank; verification does, but only Railway grants it. `--only search` prints the tier and band for each own keyword not at #1.
   - **Verdict:** nothing is decided until a checkpoint is stored. Templates are read at day 21 and P2 needs 2+ active projects (the 2026-11-01 amendment in docs/designs/day-14-template-verdict.md). The hourly snapshot run stores a checkpoint at the first decisive hour, and reading the endpoint never does. Day 45 was stored on 2026-11-09: P1 passed (3 of 5 against 2 of 25), P2 not enough data, and the Verdict column on Templates (T4) shipped the same day. Day 90 can't be judged before 2026-12-24. Report a new checkpoint when one is stored, and record a failed predictor in the design doc: when the latest checkpoint fails P1, every `keep` turns into `no signal`. Never move a threshold or the judging moment after seeing the numbers.
4. If the figures moved a lot, offer to refresh the checklist page. Edit `page.html` here (the figures strip, the step numbers, the dates table), read the artifact first with Artifact `action: "read"` and that URL, then publish `page.html` with `url` set to it.

Don't advise against an original on kickback math alone. The owner values originals for themselves.
